ACTUALIZACIÓN V2.17.0: red vial poligonal y semáforo con degradado.

2. REQUISITOS E INSTALACIONES
==============================================================================

Backend (ya instalado en este repositorio)
  - Node.js 20 o superior (probado con 22 y 24).
  - npm install en backend/ instala:
      compression   ^1.8.2
      nodemailer    ^10.2.1
      pdfkit        ^0.20.2
    (además de las dependencias que ya existían)

  Comando ejecutado:
      cd backend
      npm install nodemailer pdfkit compression --save

Escritorio (ya instalado en desktop/)
  - Node.js 20 o superior.
  - npm install en desktop/ instala:
      electron          ^33.0.0
      electron-builder  ^25.1.8

  Comando ejecutado:
      cd desktop
      npm install

  Nota: electron-builder arrastra dependencias de desarrollo con avisos de
  auditoría. No afectan al runtime de la app; para revisarlas:
      cd desktop
      npm audit

Sistema operativo para empaquetar
  - Windows: sin herramientas adicionales; NSIS se descarga solo.
  - Linux: dpkg y fakeroot para el .deb; libfuse2 para ejecutar el AppImage.

Docker (opcional)
  - docker compose up -d --build
  - La imagen ya incluye las dependencias nuevas porque se instalan con
    npm ci --omit=dev.

3. VARIABLES DE ENTORNO NUEVAS
==============================================================================

Copiar .env.example a .env (raíz) y a backend/.env, y completar:

  # Correo
  MAIL_ACTIVO=true
  MAIL_DRY_RUN=false                 # true = no envía, solo registra
  SMTP_HOST=smtp.tu-proveedor.mx
  SMTP_PORT=587
  SMTP_SECURE=false                  # true solo para puerto 465
  SMTP_USER=tu-usuario
  SMTP_PASS=tu-contraseña-o-app-password
  MAIL_FROM=Sistema de Incidencias <no-reply@tu-dominio.mx>
  MAIL_REPLY_TO=contacto@tu-dominio.mx
  CORREO_MAX_POR_MINUTO=20
  CORREO_MAX_REINTENTOS=3

  # Enlaces de los correos
  URL_PUBLICA=https://incidencias.tu-dominio.mx

  # Formularios públicos
  LIMITE_SOLICITUDES_HORA=5
  LIMITE_CONSULTAS_HORA=30
  RATE_LIMIT_MAX_PUBLICO=10

Si SMTP_HOST está vacío o MAIL_DRY_RUN=true, el sistema funciona igual: los
correos se registran como «simulado» en la tabla envios_correo y en el log.
Esto es útil para desarrollo y pruebas.

5. CORREO SMTP: TUTORIAL PASO A PASO
==============================================================================

El correo se usa para:
  - confirmar solicitudes públicas de informe (doble opt-in);
  - enviar el PDF/CSV generado;
  - avisar de mensajes de contacto y respuestas;
  - enviar mensajes internos admin↔funcionario;
  - responder sugerencias;
  - (opcional) campañas de promoción con baja en un clic.

5.1 Gmail / Google Workspace
  1. Activa la verificación en dos pasos en la cuenta.
  2. Google Account → Seguridad → Contraseñas de aplicaciones.
  3. Crea una contraseña para «Correo» y cópiala.
  4. Configura:
        SMTP_HOST=smtp.gmail.com
        SMTP_PORT=587
        SMTP_SECURE=false
        SMTP_USER=tu-cuenta@gmail.com
        SMTP_PASS=la-contraseña-de-aplicación
        MAIL_FROM=Sistema de Incidencias <tu-cuenta@gmail.com>
  Límite de Gmail: ~500 destinatarios/día en cuentas gratuitas y ~2000 en
  Workspace. Ajusta CORREO_MAX_POR_MINUTO a 10–20.

5.2 Zoho Mail
        SMTP_HOST=smtp.zoho.com
        SMTP_PORT=587
        SMTP_SECURE=false
        SMTP_USER=tu-cuenta@tu-dominio.mx
        SMTP_PASS=tu-contraseña

5.3 Servidor propio (Postfix, Mailcow, etc.)
        SMTP_HOST=mail.tu-dominio.mx
        SMTP_PORT=587
        SMTP_SECURE=false
        SMTP_USER=no-reply@tu-dominio.mx
        SMTP_PASS=...
  Asegúrate de que el servidor acepta autenticación y de que el firewall
  permite salir al puerto 587 (o 465 con SMTP_SECURE=true).

5.4 Buenas prácticas de entregabilidad
  - Publica registros SPF, DKIM y DMARC del dominio remitente.
  - Usa un remitente real (no-reply@tu-dominio.mx), no un correo personal.
  - No compres listas de correos. Para promoción, usa doble opt-in y baja en
    un clic.
  - Empieza con volúmenes bajos (CORREO_MAX_POR_MINUTO=10) y súbelos poco a
    poco.
  - Revisa la tabla envios_correo y la carpeta de rebotes.

5.5 Probar sin enviar
        MAIL_DRY_RUN=true
  Luego pide un informe desde /informes y revisa:
        GET /api/admin/correos   (como administrador)

6. ROLES Y ALCANCE TERRITORIAL
==============================================================================

Roles:
  anonimo          sesión sin cuenta; puede reportar, comentar y denunciar.
  ciudadano        cuenta con correo; ve todo el país y edita lo suyo.
  funcionario      escritura dentro de sus municipios asignados.
  auditor          solo lectura sobre municipios/estados asignados.
  enlace_estatal   solo lectura sobre todos los municipios de sus estados.
  enlace_federal   solo lectura sobre los municipios de sus estados.
  admin            alcance global; gestiona cuentas y alcances.

Reglas:
  - Un funcionario con un municipio solo ve ese municipio.
  - Un funcionario con varios municipios puede alternar entre ellos.
  - Un funcionario NO puede registrar ni consultar fuera de su ámbito.
  - Un auditor no puede crear reportes, cambiar estados, resolver, moderar,
    comentar ni denunciar.
  - Un enlace estatal/federal ve los municipios de sus estados y no puede
    escribir.
  - Los ciudadanos y las sesiones anónimas ven todos los municipios y estados.
  - El admin puede acotarse temporalmente a un municipio activo.

Asignar alcance desde el panel:
  Panel → Usuarios → Nuevo/Editar.
  - Municipios asignados: Ctrl/Cmd para seleccionar varios.
  - Estados asignados: para enlaces estatales/federales.
  - «Permitir escritura»: solo aplica a funcionarios; los roles de lectura
    siempre quedan en solo lectura.

API:
  POST /api/usuarios
  PATCH /api/usuarios/:id
  Campos: rol, municipios (array de ids), estados (array de nombres),
          puedeEscribir (bool), municipioId (compatibilidad, municipio
          principal), correo, password, activo.

7. INFORMES PÚBLICOS POR SOLICITUD
==============================================================================

Flujo:
  1. El ciudadano entra a /informes (sin sesión).
  2. Elige municipio o estado, fechas, tipos, ámbito y formato (PDF/CSV).

  - Una solicitud abierta por correo para evitar duplicados.
  - Reintentos de generación: CORREO_MAX_REINTENTOS.

Bloqueos:
  - El administrador puede bloquear un correo o una IP (hash), con motivo y
    caducidad opcional.
  - El bloqueo impide nuevas solicitudes y se puede revertir.

8.1 CAMPAÑAS DE PROMOCIÓN POR CORREO
==============================================================================

Objetivo: promocionar el servicio sin violentar la LFPDPPP ni las políticas
anti-spam. El sistema NUNCA importa listas compradas: las altas entran por el
formulario público y solo reciben correos quienes confirman su dirección.

Cómo funciona
  1. La persona entra a /suscripcion.html (hay un enlace desde /informes) y
     deja su correo y, si quiere, su municipio.
  2. Recibe un correo de confirmación (doble opt-in). Sin esa confirmación su
     suscripción queda «pendiente» y NO entra en ningún envío.
  3. Al confirmar, la suscripción queda «activa» con un token único que sirve
     también para darse de baja en un clic desde cualquier campaña.
  4. El administrador crea la campaña en el panel → pestaña «Campañas»:
       - nombre interno, asunto y HTML;
       - segmento: todos, un municipio o un estado;
       - vista previa y envío de prueba a su propio correo;
       - envío final por lotes.
  5. Cada mensaje lleva cabecera del sistema, aviso de privacidad y enlace de
     baja. La baja es inmediata y el correo sale de los siguientes segmentos.
  6. La lista de bloqueos de solicitantes (sección 7) actúa como lista de
     supresión: un correo bloqueado tampoco recibe campañas ni puede
     suscribirse.

Límites y garantías
  - El envío respeta CORREO_MAX_POR_MINUTO (por defecto 20).
  - Si no hay SMTP configurado o MAIL_DRY_RUN=true, el envío se registra como
    «simulado» y no sale nada: sirve para probar el flujo.
  - Una campaña enviada no se puede editar ni reenviar (queda como bitácora).
  - El token de baja no se expone en la API de administración.
  - Los envíos quedan en envios_correo con tipo «campana».

Migración
  - 015_campanas_correo.js crea suscripciones_correo, campanas_correo y
    campana_destinatarios. Es reversible con migrate:rollback.

Endpoints
  Públicos:
    POST /api/publico/suscripciones            (alta con doble opt-in)
    POST /api/publico/suscripciones/confirmar  (token del correo)
    POST /api/publico/suscripciones/baja       (baja en un clic)
  Administrador:
    GET    /api/admin/campanas
    GET    /api/admin/campanas/resumen
    GET    /api/admin/campanas/:id
    POST   /api/admin/campanas
    PUT    /api/admin/campanas/:id
    POST   /api/admin/campanas/:id/prueba
    POST   /api/admin/campanas/:id/enviar
    GET    /api/admin/suscripciones

Recomendaciones legales
  - Publica el aviso de privacidad y conserva la evidencia del consentimiento
    (la tabla guarda fecha de alta, confirmación, baja y hash de IP).
  - No uses las campañas para asuntos internos: para eso está la mensajería.
  - Revisa el dominio remitente (SPF/DKIM/DMARC, sección 5.4) antes de enviar
    a más de unas decenas de personas.

11. MAPAS OFFLINE: VEREDICTO LEGAL Y GENERACIÓN
==============================================================================

VEREDICTO
  NO se pueden descargar masivamente teselas de tile.openstreetmap.org,
  OpenTopoMap ni Esri. La política de la OpenStreetMap Foundation prohíbe el
  «bulk downloading» y el uso de sus teselas por aplicaciones distribuidas sin
  permiso. Hacerlo puede bloquear la IP y supone incumplir sus términos.

SOLUCIÓN LEGAL, SIN COSTO Y OPEN SOURCE
  1. Descargar un extracto .osm.pbf de Geofabrik (datos ODbL).
  2. Generar teselas propias con tilemaker o planetiler.
  3. Empaquetarlas como PMTiles.
  4. Servirlas desde la app en 127.0.0.1 (ya implementado en
     desktop/src/mapas.js) y consumirlas con protomaps-leaflet.
  5. Mantener la atribución «© OpenStreetMap contributors» y el aviso ODbL.

  Las teselas rasterizadas son un «Produced Work»: la obligación principal es
  atribuir. El archivo .pmtiles contiene una base derivada; si se redistribuye,
  hay que compartir también la receta de generación (el script incluido) y
  mantener la licencia ODbL.

TAMAÑOS ORIENTATIVOS
  - CDMX + Michoacán + Guanajuato, vectorial z0–14: 150–400 MB.
  - México completo, vectorial z0–14: 2–4 GB.
  - Raster equivalente: decenas de GB (no recomendado).

PROCEDIMIENTO
  Requisitos:
    - tilemaker >= 2.4  (https://github.com/systemed/tilemaker)
    - pmtiles CLI       (npm install -g pmtiles)
    - ~1 GB de disco para el extracto de México

  Comandos:
      cd desktop
      node scripts/generar-mapas-offline.mjs --descargar
      # o con un extracto propio:
      node scripts/generar-mapas-offline.mjs --osm C:\datos\mexico.osm.pbf

  El resultado queda en:
      desktop/recursos/mapas/incidencias.pmtiles

  Vuelve a empaquetar la app:
      npm run dist:win
      npm run dist:linux

  La app detecta el paquete al arrancar y expone la URL local en
  desktopApi.info(). Si no hay paquete, usa las teselas online del servidor.

CACHÉ ONLINE
  Solo se cachea lo que el usuario ve de forma natural (caché HTTP). Nunca se
  precargan teselas de forma masiva.

14. SEGURIDAD Y PRIVACIDAD
==============================================================================

  - El alcance territorial se resuelve en el servidor en cada petición; no se
    confía en el JWT para el rol ni para los municipios.
  - Los roles de lectura no pueden mutar nada (middleware + servicios).
  - Los informes públicos excluyen autoría y datos personales.
  - Los bloqueos guardan un hash de la IP, no la IP en claro.
  - Las solicitudes tienen doble opt-in y una sola solicitud abierta por correo.
  - El correo se limita por minuto para no saturar el SMTP.
  - La app de escritorio usa contextIsolation + sandbox y no expone Node.
  - La CSP permite el servidor local de mapas (127.0.0.1) pero no teselas de
    OSM/Esri adicionales.
  - Sigue siendo obligatorio cambiar JWT_SECRET y DB_PASSWORD en producción.
  - Revisa el aviso de privacidad y la base legal del tratamiento de correos
    (LFPDPPP en México) antes de enviar promociones.

15. REVERSIÓN Y MANTENIMIENTO
==============================================================================

  - Las migraciones 010–015 son reversibles con migrate:rollback.
  - Al revertir 010, los roles nuevos pasan a funcionario para no perder
    acceso.
  - Los archivos .pmtiles no se versionan; se regeneran con el script.
  - El histórico de métricas es en memoria: se pierde al reiniciar.
  - La cola de correo es en proceso: si el servidor se reinicia, las
    solicitudes en estado «pendiente» se retoman al arrancar.
  - Con varias réplicas haría falta un almacén compartido para rate limits y
    cola (Redis o similar). No está incluido.

Operación de respaldos
  - Los archivos se guardan en backend/data/respaldos/ y no se sirven como
    estáticos.
  - El worker revisa cada 30 minutos y crea un respaldo automático cuando se
    cumple respaldos.intervalo_horas (24 h por defecto), aplicando
    respaldos.retencion (7 por defecto).
  - La restauración reemplaza los datos actuales; siempre crea antes un
    respaldo previo_restauracion y exige escribir RESTAURAR.
  - En producción: programar una ventana de mantenimiento, descargar el
    respaldo previo y verificar los conteos después de restaurar.

Seguridad
  - El simulador solo lo abre el admin maestro. Las acciones usan los servicios
    reales, pero los datos quedan con simulado=1 y simulacion_id, y las listas
    públicas los excluyen. Revertir borra únicamente esos datos.
  - Los routers montados en la raíz aplican requiereAdmin por ruta, no con
    router.use, para no bloquear peticiones de otros roles.
